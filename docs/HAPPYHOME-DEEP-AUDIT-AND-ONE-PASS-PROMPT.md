# Happy Home — глубокий аудит и промпт на завершение за один проход

**Дата аудита:** 2026-11-27
**Репозиторий:** `miagpt/game`
**Рабочая ветка:** `arena/3ec9652b-game` — активная; базовый коммит `ccde8cb`
**Назначение:** зафиксировать фактическое состояние и дать следующему coding-agent самодостаточный промпт, который направляет его от аудита до проверки и публикации, а не только к очередному прототипу.

> Это аудит репозитория и исходников, а не сертификат доступности, реальный плейтест или доказательство совместимости с физическим iPhone. Те проверки, которые нельзя выполнить в окружении агента, должны быть явно названы ограничением — их нельзя «засчитать» по наличию автотеста.

## 1. Краткое заключение

**Актуализация 2026-11-27:** этот документ фиксирует исходный глубокий аудит; ниже сохранены исторические находки и промпт для воспроизводимости. Код после аудита заметно изменён: добавлены самостоятельные игровые правила для 50 именованных паттернов, несколько специальных эффектов, многофазные подсказки боссов, полное ограниченное сохранение checkpoint, текстовая доступность Canvas, тесты скрытой вкладки и расширенные мобильные mock-E2E. Не следует считать, что этим доказана ручная проходимость всех механик/боссов.

Happy Home открывается с корневой страницы и содержит 5 глав × 10 раундов, локальные портреты, сенсорное управление, звук и сохранение. `npm test`, `npm run test:e2e`, синтаксическая проверка JS, `npm run build` и `git diff --check` успешно завершились локально 2026-11-27. Это **не подтверждённый публичный релиз**: настоящий iPhone/Safari плейтест, GitHub Actions на PR и Pages deployment/production URL ещё не подтверждены.

### Проверенное состояние в этой рабочей копии

- Корневой `index.html` запускает Happy Home; `happy-home/index.html` оставлен для вложенного маршрута; legacy-страницы Поршика сохранены.
- `happy-home/content.js`: 5 возрастных уровней, 50 уникальных названий и кодов паттернов, 5 boss-флагов, целевая длительность растёт примерно на 10% на шаг. Раунд 1 уровня 1 — 120 с; раунд 10 — 283 с (4:43).
- Портреты локальные WebP; приложение не включает исходные фотографии.
- Последний полный прогон: `npm test` — 70/70; `npm run test:e2e` — legacy E2E, Happy Home gameplay и mobile/boss smoke tests для всех 50 паттернов и пяти босс-сцен; `npm run build` — 72 файла, около 5.3 МБ. Все E2E используют browser-free DOM/Canvas mocks, а не полноценный браузер.
- Mobile smoke test задаёт mocked viewport 320×390; это проверка JS/runtime, но не реальной CSS-раскладки и не iPhone Safari.
- Автоматически проверены HTTP-страницы локально в предыдущем проходе; production GitHub Pages URL не проверен.
- Pages workflow запускается на `main` и вручную; текущая ветка не опубликована.

## 2. Находки аудита — закрыть до объявления готовности

### P0 — соответствие фото и персонажей

В ранее подтверждённом пользовательском контексте визуальная привязка была уточнена так: **Арчи — чёрно-рыжий пёс с острыми ушами; Грэйс — серый пёс с белой грудью**. В текущих игровых WebP файлах визуально наоборот: `archie.webp` показывает серого пса с белой грудью, а `grace.webp` — чёрно-рыжего остроухого пса. `content.js` также описывает Арчи как серого, Грэйс как чёрную.

**Действие:** сверить с предоставленными референсами/предшествующим подтверждением и исправить привязку файла/портрета/текста во всех точках отображения. Не менять заданные владельцем текущие возраста и порядок уровней; возраст не выводить из фото. Если оригинальные референсы недоступны в рабочем пространстве, использовать эту зафиксированную коррекцию как источник правды и не утверждать, что портреты окончательно сверены с оригиналами.

### P0 — механики в описаниях и механики в коде

`content.js` задаёт 50 разных `pattern`, но отдельные паттерны не находились в `app.js`: `soft-fog`, `sun-combo`, `mirror-route`, `dusk-combo`, `twilight-combo`, `moon-gravity`, `guardian-rehearsal`, `memory-colors`, `marked-boxes`, `boss-replay`. Некоторые остальные используют только базовую генерацию ворот. Это значит, что уникальные тексты могут обещать эффект, которого игрок не увидит.

**Действие:** составить таблицу `round id → brief/mechanic → реальная игровая функция/визуальная телеграфия → тест`. Реализовать все заявленные механики хотя бы в простом, читаемом MVP-виде или честно переписать тексты/дизайн так, чтобы они соответствовали реальным правилам. Не оставлять ключи паттернов декоративными метками без игровой логики.

### P0 — пять боссов пока не пять отдельных босс-испытаний

В `drawBoss()` есть пять вариантов рисунка; общая boss-фаза включается примерно на 77% раунда. Прогресс в основном общий: собирать светящиеся лапки/отметки. Ветер имеет общий модификатор, но отдельные многофазные состояния из дизайн-документа не подтверждены. После трёх добавочных отрезков код может автоматически открыть путь. E2E проверяет рендер всех пяти босс-сцен, но не телеграфирование, уникальную механику, фазовую победу, восстановление после ошибки или завершение босса.

**Действие:** каждому боссу — отдельная конечная машина/паттерн с заметным предупреждением, одной понятной целью, несколькими фазами, локальным мягким повтором фазы и гарантированным доступным способом завершения. Проверять победу автоматизированным игроком/симулятором и браузерным E2E, а не только наличие иллюстрации. Помощь команды допустима, но должна быть видимой и не подменять все boss-механики одинаковым таймером.

### P0 — чекпоинт не восстанавливает прогресс сегмента

`save.checkpoint` хранит `{ id, elapsed }`. При возобновлении заново задаются позиция героя, жизни, количество подобранного, `bossHits`, расширения времени и прочее состояние. Это не равно восстановлению на контрольной точке, описанному в ТЗ. Вызов при `visibilitychange` ставит игру на паузу, но следующий запуск начинает с округлённого времени и начального состояния раунда.

**Действие:** определить минимальное детерминированное состояние чекпоинта: round/seed/elapsed/segment, позиция и скорость или их нормализованные значения, остаток жизней/защиты, собранные цели и boss phase; сохранять атомарно на чекпоинте, pause, завершении и `visibilitychange`. Ограничивать/валидировать входящие данные. Написать тесты fresh/corrupt/старый save/возобновление/недоступный localStorage.

### P0 — реальная iPhone-проверка отсутствует

В CSS есть `100svh`, `viewport-fit=cover` и `touch-action:none` на игровой поверхности; минимальная ширина body — 320px, кнопки игры в основном 44×44px. Но в `happy-home/style.css` не найдено `env(safe-area-inset-*)`, нет подтверждённого поведения landscape/выреза, а JSDOM не выполняет реальную раскладку CSS. `prefers-reduced-motion` уменьшает CSS-анимации, но Canvas продолжает рисовать движущиеся элементы/частицы. Реальный iPhone Safari не тестировался.

**Действие:** добавить safe-area отступы и fallback viewport, определить поведение при повороте/сворачивании; учесть reduced motion в Canvas (меньше/статичнее фон, но сохранить различимость угроз); провести реальные браузерные проверки на 320, 375/390 и крупном мобильном viewport и на iPhone, если устройство доступно. Отдельно записать физическое устройство/iOS/Safari и результаты. Эмуляцию никогда не выдавать за физический тест.

### P1 — доступность/ввод

- Кнопки музыки, звуков и паузы имеют ориентир 44×44px; это больше минимального размера 24×24 CSS px из WCAG 2.2 SC 2.5.8. Это полезная проверка размеров, но само по себе не доказывает WCAG conformance.
- Основное управление вызывает взмах на `pointerdown`; отдельного `pointercancel` listener нет. Текст раунда добавлен как `aria-live="polite"`; canvas остаётся визуальным игровым полем, а состояния/предупреждения боссов, прогресс и ошибки почти полностью canvas-only.
- Карточки глав сделаны `article role=button`, но стоит проверить корректное имя/состояние/объявление блокировки screen reader-ом.
- Мелкие подписи/таймер/карточки требуют проверки контраста, масштаба текста и увеличения до 200%.

**Действие:** проверить клавиатуру, видимый focus, screen reader, нецветовые сигналы, уместный `pointercancel`, крупный текст и WCAG 2.2 AA-критерии релевантных экранов. Задания, предупреждения, здоровье, пауза и boss phase должны иметь доступную текстовую альтернативу. Не блокировать прокрутку сайта вне игрового холста.

### P1 — звук и жест пользователя

Настройки `music`/`sfx` сохраняются отдельно; `playMusic()`/`tone()` используют Web Audio. В конце загрузки вызывается `playMusic()`, если настройка из localStorage включена: это пытается создать/возобновить `AudioContext` до нового жеста пользователя. Браузер может это заблокировать, но требование «аудио запускается после жеста» лучше обеспечить явно, а не полагаться на блокировку autoplay.

**Действие:** до первого пользовательского жеста не создавать/не resume `AudioContext`; сохранённую настройку отображать, а аудио запускать на первом разрешённом жесте. Музыку глушить на hidden/pause, независимый mute тестировать после reload, проверять WebKit/Safari. Ни одно игровое предупреждение не должно быть только звуковым.

### P1 — offline/cache и иконка

`sw.js` содержит старые legacy ресурсы и не содержит новый `assets/img/happyhome-icon.svg`; новая корневая игра не регистрирует этот service worker, поэтому офлайн-режим Happy Home не обещан. Вложенный HTML указывает SVG как `apple-touch-icon`, хотя надёжнее использовать PNG для iOS home-screen icon либо убрать эту ссылку, поскольку установка не является требованием.

**Действие:** решить, нужна ли вообще офлайн/PWA поддержка (не обязательна). Если нет — не обещать offline, убрать некорректную apple-touch ссылку; если да — добавить актуальные маршруты/иконку, поднять cache version и тестировать реальную установку/обновление. Не ломать legacy страницы.

### P1 — release workflow и фактическая публикация

`pages.yml` использует правильный общий шаблон: artifact build/upload, отдельный deploy job, `pages: write`, `id-token: write`, `actions/deploy-pages@v4`. Но триггер публикации — `main` или `workflow_dispatch`; ветка разработки сама по себе это не публикует. CI работает на PR и push в `main`.

**Действие:** после приёмочных тестов открыть PR из текущей ветки в `main`; дождаться успешных CI и Pages deployment; сверить URL из deployment output, открыть опубликованный сайт и проверить root/вложенные маршруты, ассеты и Console/network. Отчитываться «опубликовано» только после успешного deploy и проверки фактического URL.

### P2 — полировка и документация

- Для главной страницы Happy Home отсутствуют OG/Twitter metadata, а социальное превью/корневой favicon следует проверить на актуальность.
- `site.webmanifest` и сервис-воркер частично относятся к старому сайту. Не позиционировать старый PWA manifest как новый Happy Home.
- Основная игра собрана в одном `happy-home/app.js` (369 строк на момент аудита): UI, Canvas, симуляция, ввод, звук и сохранение связаны. Не требуется переписывать ради архитектуры, но при разработке сложных фаз выделить чистые функции правил/симуляции и проверяемые модули.
- Текущие тесты и документы не доказывают длительность 50 реальных прохождений или плейтест; 2:00 → 4:43 — design target, а не измеренный факт.

## 3. Исследовательские выводы и применённые источники

Исследование ограничено первичными техническими источниками на GitHub и фактическим кодом проекта.

1. **Размер интерактивной цели.** В исходнике WCAG 2.2 SC 2.5.8 задан минимум 24×24 CSS px с перечисленными исключениями. Текущие основные игровые кнопки около 44×44 CSS px — хороший запас по размеру, но это не заменяет проверку spacing, контраста, focus, semantics и прочих критериев. [W3C WCAG source: Target Size (Minimum)](https://github.com/w3c/wcag/blob/main/guidelines/sc/22/target-size-minimum.html)
2. **Pointer cancellation.** WCAG 2.1 SC 2.5.2 описывает варианты отмены/undo, up-event и essential функции. Игровой взмах на down-event может быть существенной частью управления, но UI-действия и касания вокруг Canvas всё равно нужно проверять на случайных срабатываниях/отмене. [W3C WCAG source: Pointer Cancellation](https://github.com/w3c/wcag/blob/main/guidelines/sc/21/pointer-cancellation.html)
3. **Pages deployment.** Документация официального `actions/deploy-pages` описывает деплой предварительно загруженного Pages artifact и рекомендуемый отдельный deploy job с `pages: write` и `id-token: write`; эти основы в проектном workflow уже присутствуют. Следовательно, главный release gap — не переписывать workflow вслепую, а пройти успешный реальный pipeline и проверить результат. [Official action README](https://github.com/actions/deploy-pages/blob/main/README.md)
4. **Обязательный пользовательский ТЗ в репозитории.** `docs/HAPPYHOME-DESIGN.md` — наиболее подробный source of truth: 5×10, длительности, пять босс-концепций, iPhone UX, offline/сохранение, accessibility и ручная приёмка. Промпт ниже не должен сокращать или подменять его.

Дата просмотра доступных GitHub-источников: 2026-11-27. Внешние runtime-библиотеки/CDN из исследования не добавлять.

Сейчас текущие файлы визуально выглядят наоборот (`archie.webp` — серый, `grace.webp` — чёрно-рыжая): обязательно исправь, сохранив названия/возраста/порядок; проверь корневой и вложенный маршруты, карту, игровое поле и E2E.
